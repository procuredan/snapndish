# Stage 1B staging release

This is an isolated capability test. It does not change the verified Stage 1A Live Lab at `app.snapndish.com`. Do not deploy Stage 1B to that hostname without a separate explicit production authorization. GitHub publication, CI and Cloudflare deployment are separate gates.

## Resources and access

Create a new Snap n Dish Worker, D1 database and private R2 bucket named for Stage 1B staging. Use `stage1b/migrations/` only for its D1 binding; `live-lab/migrations/` remains Stage 1A only. Put actual created resource IDs into a Stage 1B staging Wrangler config only after `wrangler whoami` confirms the intended Snap n Dish account. Never reuse Stage 1A or Snap n Done IDs. The Worker must use `STAGE1B_ENABLED=true`, `BEHAVIOR_VERSION=stage1a-snap-v2`, `ARM=C`, and the pinned text/realtime models recorded in source. Enable the minute cron for the one return reminder experiment.

Keep staging behind an owner-only Cloudflare Access policy before opening the full Worker. Protect the Worker itself, including its `workers.dev` route; do not protect all Workers in the account or alter the Stage 1A Live Lab. This edge gate is test-environment access control, not product registration. Confirm an unauthenticated browser cannot reach chat or review, and an approved browser can. Cloudflare documents [per-Worker Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/); this Worker uses HTTP for SDP and API calls, with direct WebRTC media to OpenAI, so it does not require a WebSocket upgrade through the Access-protected Worker. If Zero Trust is unavailable, keep the Worker closed and resolve access before running live voice.

Secrets for this staging Worker are `OPENAI_API_KEY`, `LAB_ACCESS_CODE` for owner review only, `COOKIE_SIGNING_KEY`, `VAPID_PRIVATE_JWK`, `VAPID_PUBLIC_KEY`, and `VAPID_SUBJECT`. The public VAPID key and subject may be non-secret bindings, but the private JWK must be a managed secret. Do not print secrets, include them in commands, copy a Stage 1A signing key, or put them in GitHub. Use a dedicated OpenAI project spending limit where available; the Worker’s text limits alone do not constrain a direct Realtime media session.

## Ordered gates

1. Inspect the exact GitHub branch, clean local tree, green verification-only CI, existing Stage 1A live health/version, and `wrangler whoami`. Run `npm test`, `npm run preflight:v2`, `git diff --check`, and a Stage 1B bundle dry run. Preserve the Stage 1A corpus/results and v2 Worker version.
2. Confirm Stage 1B staging names are unused. Create the separate D1 database and R2 bucket. Record only resource names/IDs in the staging config. Confirm no production data is copied. Inspect the new D1 migration ledger, apply `stage1b/migrations/0001`–`0007`, and verify the ledger and baseline schema. Record a D1 recovery point before later additive migrations.
3. Deploy `stage1b/closed.mjs` first with the Stage 1B staging config and record its Worker version ID. Verify the Worker returns only 503 and no data. Set the staging secrets while this version is closed; secret writes can create new Worker versions, so recheck the active version and response.
4. Enable the owner-only Cloudflare Access policy and verify its denial/allow paths, then deploy the full Stage 1B Worker. Record the new Worker version and confirm `/health` reports `1B-staging` and `stage1a-snap-v2` only after Access approval.
5. Verify a rendered streamed v2 text turn and Good / Missed It; interruption/reload replay; private photo upload and visual reasoning; accepted meal revision and stale-result rejection; spoken input, spoken reply and same visible transcript; one-use phone → computer/tablet → phone continuation; a permissioned reminder after the app is closed returning to the correct conversation; private `/review` and D1/R2 telemetry. Measure latency, usage/cost and culinary quality for each. Test Access from an ordinary unauthenticated browser and verify it cannot use model APIs or read review data.
6. Check retention and error telemetry, then report the five proof outcomes and limits to PM. Stop. No commercial-alpha or Stage 1A/live promotion follows from this staging experiment.

## Rollback

Before opening the full Worker, record the exact closed Stage 1B Worker version ID. If a staging defect or cost/privacy issue appears, roll back **only** the Stage 1B staging Worker to that closed version using `wrangler rollback CLOSED_VERSION_ID --config STAGE1B_STAGING_CONFIG --name snapndish-stage1b-staging --message 'Pause Stage 1B staging' --yes`. Verify its URL returns 503 and model/review APIs are unavailable. The Stage 1A Live Lab is not in this rollback path. Code rollback does not reverse D1 or R2; preserve diagnostic evidence, decide whether to restore D1 to the recorded point, and delete expired images through the authorized retention path. The closed Worker does not run retention cleanup; resume the working Worker or run a reviewed cleanup after incident containment.
