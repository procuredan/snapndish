## Approved extension and expected staging behavior

- **Local candidate:** Additive migration `0011_dashboard_foundation.sql` makes a durable synthetic owner row independent of expiring session/customer rows, an immutable accepted recipe version, a cook instance per source session, selection history, collection/settings foundations, and an idempotent operation record. An `AFTER UPDATE` trigger observes successful complete package acceptance inside the existing D1 transaction. Failed and stale proposals do not reach it. The live session remains authoritative; a one-way cooking progress snapshot is only for history. No recipe row or collection membership is fabricated for an empty state.
- **Dashboard:** A staging-only feature flag places five navigable sections above the existing conversation. Today lists accepted selections for the browser's current calendar day. Shopping opens the current accepted session checklist. History opens the immutable stored plan while explicitly saying cooking is unconfirmed. Future Cooks and Favorites show truthful empty states until later authorized actions exist. Image cards show a non-food fallback when no rights-verified photo exists. Snap It, Write It and Talk It call the existing entry paths.
- **Ownership limit:** The existing protected anonymous staging cookie scopes reads. The durable owner ID survives session cleanup, but the recipe cannot be recovered by that person after the anonymous customer cookie expires until a separately approved identity migration is built. This is a synthetic staging foundation, not a commercial account. No earlier accepted packages are backfilled.
- **Deferred:** Multiple independent cooks, consolidated Shopping, configurable daily reset, deliberate collection actions, conversational recipe retrieval, licensed image matching, real customer authentication, deletion executor, culinary learning, payments and paid tiers. The approved visual mockups were not located in accessible repository or architecture records; visual fidelity to those mockups remains unverified.

## Identity feasibility investigation — no activation

- Better Auth documents a Cloudflare D1 database example and an email OTP plugin. Resend documents sending transactional email from a Cloudflare Worker. Google web sign-in requires an OAuth client ID and backend ID-token verification. Apple's web sign-in requires an Apple Developer Services ID tied to a primary App ID and registered domains/return URLs. This combination is technically plausible but no provider, credentials, domains or integration code is approved for Milestone 1.
- A separate reviewed plan must specify provider ownership and credentials, email delivery/domain, account recovery, unique provider-subject linkage, explicit account linking, session rotation, anonymous-recipe claim, cross-device ownership, account deletion and retention/backups. Matching email addresses alone must not merge owners. The current cookie cannot satisfy those requirements.
- Primary documentation: [Better Auth database](https://better-auth.com/docs/concepts/database), [Better Auth email OTP](https://better-auth.com/docs/1.6/plugins/email-otp), [Cloudflare Resend guide](https://developers.cloudflare.com/workers/tutorials/send-emails-with-resend/), [Google web sign-in setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid), [Apple web configuration](https://developer.apple.com/documentation/signinwithapple/configuring-your-environment-for-sign-in-with-apple).

## Release gates and recovery

1. Review the migration against the exact remote schema and existing session cleanup. It is additive and has no foreign key to expiring rows. Do not assume a Worker code rollback reverses D1 schema or durable data.
2. Run local tests, browser layout/journey checks and dry-run build. Push the reviewed branch and require exact-source GitHub CI success.
3. Recheck the active staging version, Access boundary, migration ledger and a **fresh** D1 bookmark immediately before applying `0011` remotely. Apply only to isolated staging D1. Minimize the interval before candidate Worker deployment because an existing V5.1 Worker will also trigger persistence after `0011` is applied.
4. Deploy only the exact reviewed candidate to `snapndish-stage1b-staging`. The existing V5.1 Worker is a functional code rollback with the additive schema; it continues culinary behavior and can create history through the D1 trigger, but removes the new dashboard UI. The closed Worker is containment if Access/privacy fails. Restore the D1 bookmark only as a separate incident decision after assessing newly accepted staging data.
5. Verify the actual rendered dashboard, navigation, existing culinary conversation and accepted package, Shopping, reload, owner isolation, telemetry, effective behavior and deployed Worker UUID. Preserve only synthetic or redacted evidence. If a gate fails, stop and report it; do not deploy to production.
